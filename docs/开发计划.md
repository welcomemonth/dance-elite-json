## Phase 0：基础设施与数据层

### T1 后端基础设施（SQLite / 迁移 / 统一响应 / 中间件）

**目标**：把现有 JSON 文件存储的 `internal/store` 重建为 SQLite 数据层，建立所有后续任务的工程地基。

**上下文**：go.mod 目前无 SQLite 驱动，选 `modernc.org/sqlite`（纯 Go，Docker 交叉编译无需 CGO）。复用现有 `cmd/dance-elite/main.go`、`internal/configs`（viper）、`internal/pkg/logger`（zap）骨架。

- [x] 引入 `modernc.org/sqlite` 驱动，封装 `internal/store`：连接打开、PRAGMA（WAL、外键开启 busy_timeout）、单例管理
- [x] 实现迁移框架：按文件名版本序执行 `migrations/00xx_xxx.sql`，记录 `schema_migrations` 表，支持重复启动幂等
- [x] 实现统一响应包装 `{"code", "message", "data"}` 与全局错误码（对照 API 文档 0.3/0.4），error → HTTP status 映射中间件
- [x] 实现基础中间件：RequestID、访问日志（gin + zap 复用现有 logger）、Recovery
- [x] 配置扩展：`configs/config.yaml` 增加 `database.path`、`wechat`、`pay` 段落（先留空结构，T3 填值）
- [x] 编写 store 层接口约定文档注释（事务边界由调用方 service 控制，store 提供 `WithTx` 助手）
- [x] 单元测试：迁移幂等性（重复 Run 不产生错误）、错误包装映射

### T2 数据库 Schema 全量落地

**目标**：按《数据库表结构设计 v2/v3》创建全部表与约束。榜单域表本阶段只建表不使用（T28/T29 使用）。

**上下文**：SQLite 单写入者天然串行，事务内做名额比较即可。证件号只存 HMAC 哈希，全库无明文。

- [x] 用户与选手：`users`（openid UNIQUE）、`players`（player_no UNIQUE、id_card_hash UNIQUE、merged_into）
- [x] 赛事域：`seasons`、`events`（时间线 5 节点、score_rules/prize_rules JSON、audio_review_token UNIQUE）、`event_groups`（**增加 `taken` 字段：已占名额计数，默认 0**）
- [x] 报名支付域：`registrations`（含 8 个资料字段）、`orders`、`payments`（transaction_id UNIQUE）、`refund_tickets`、`waitlists`、`cs_tickets`
- [x] 榜单域（建表即可）：`boards`、`results`、`player_points`、`institution_points`、`final_qualifications`、`prizes`
- [x] 系统表：`admins`（username UNIQUE）、`admin_logs`、`settings`（key PK）
- [x] 部分唯一索引：`UNIQUE(player_id, group_id) WHERE status IN ('pending_payment','active')`（registrations——**必须包含 pending_payment**，否则同一人可同时挂多个待支付单）；`UNIQUE(event_id, board_id, player_id)`（results，落为 `WHERE status='published'`，纠错保留 corrected 旧记录不冲突）
- [x] 订单幂等键：`orders` 表加 `request_id` 字段 + `UNIQUE(user_id, request_id)`（防小程序网络重试重复下单，见 T9）
- [x] 所有表补 `created_at`/`updated_at`（TEXT ISO8601 本地时间，触发器或服务层写入二选一，定一种全库统一——**已定：AFTER UPDATE 触发器维护**，格式 `YYYY-MM-DDTHH:MM:SS+08:00`，部署时区 Asia/Shanghai）
- [x] 种子数据迁移脚本：`admins` 超管账号（密码 bcrypt，环境变量注入初始密码）；`settings` 默认模板（组别规则、退费政策文案、积分规则模板）
- [x] 验证：迁移后 PRAGMA foreign_key_check、schema 与文档逐表比对

> T2 落地补充（2026-11-10）：
> - 迁移文件 `0002_schema_system` / `0003_schema_users_players` / `0004_schema_seasons_events` / `0005_schema_registration_payment` / `0006_schema_ranking` / `0007_seed_settings`；超管 bcrypt 种子由 `store.DB.Seed` 在启动时幂等写入（`ADMIN_INIT_PASSWORD`，未设置则跳过，T3 改为启动自检）。

## Phase 2：赛事与组别

### T6 赛事与组别管理 API（后台）

**目标**：后台创建/编辑/发布赛事，配置组别×舞种与名额。这是报名的前置依赖。

**上下文**：状态机 draft → unpublished → registering → reg_closed → ongoing → finished / offline。时间线 5 节点强制先后。名额发布后只能调大。

- [x] 赛事 CRUD：`POST/GET/PUT /admin/events`，字段对照表结构设计（含 score_rules/prize_rules JSON 默认模板预填、可改）
- [x] 时间线校验：reg_start < reg_end < lottery < material_check < start，服务端强制
- [x] event_groups 批量配置：创建赛事时按勾选写入（level × dance_type × birth_year 从 seasons.group_rules 复制 × quota × enabled）
- [x] 状态流转接口：发布（draft/unpublished→registering，校验至少有 1 个 enabled 组别）、关闭报名（registering→reg_closed）、下线（draft/unpublished/registering/reg_closed→offline，终止态）；每次流转写 admin_logs
- [x] 名额调整：只允许调大（store 层条件 UPDATE `quota < 新值 AND 新值 >= taken` 兜底）；关闭组别开关（不影响已支付报名）
- [x] 赛季管理（简化）：seasons CRUD（`GET/POST /admin/seasons`、`PUT /admin/seasons/{id}`），active 赛季才能挂赛事；全系统同时最多一个 active 赛季（激活第二个 → 40901）；状态只按 upcoming → active → archived 向前流转，归档写 archived_at
- [x] 单元测试：时间线非法组合拒绝、状态机非法跳转拒绝、名额调小被拒

> **T6 实现要点（2026-11-11）**：
> - 状态机落地细节：publish 允许 draft/unpublished 两个来源（草稿可直接发布）；offline 为终止态，offline 后不可再编辑/流转（41012）；finished 暂无任何进入路径，留待成绩相关任务。
> - 编辑赛事的 groups 传法（API 10.3）：带 `group_id` 按 ID 定位，不带则按 `level+dance_type` 匹配已有组别；都匹配不到时草稿视为新增组合、已发布赛事拒绝（40001）。
> - 名额双 guard：service 先校验（已发布只能调大），store `UpdateQuota` 条件 UPDATE 兜底；草稿全量编辑用 `SetQuota`（可增可减但不小于 taken）。
> - 关键坑：连接池 `MaxOpenConns=1`（`:memory:` 防重建丢数据），**事务内禁止再经 `db.sql` 查询**（会自死锁），存在性检查必须用 `tx.QueryRowContext` 在同一事务连接内完成（`TransitionStatus`/`Activate` 已按此实现，后续所有 store 写方法须遵守）。
> - 错误码 41012（赛事状态不允许该操作）已加入 httpx 与 API 文档 0.5；赛季接口为新增 10.7；新增 10.1b 赛事详情接口（`GET /admin/events/{id}`）。
> - 审计 action：`admin.season.create/update`、`admin.event.create/update/publish/offline/close_registration`、`admin.event_group.quota/toggle`。
>
> **T6 审核修复（2026-11-11，第二轮）**：
> - 响应体 PascalCase → 按项目惯例建 DTO（`AdminSeasonItem`/`AdminEventItem`），并加"断言原始 JSON 键 snake_case"的防假绿测试（解码大小写不敏感会掩盖此类 bug）。
> - 编辑赛季省略日期字段时保留原值（曾把空值当清空写入 NULL）；归档赛季拒绝**任何**变更（40901，此前仅拦截状态变化）；非法 status 值 → 40001；名称 TrimSpace。
> - 状态流转与 admin_logs 合并为单一事务（`transitionWithLog`）；发布时的"≥1 enabled 组别"COUNT 校验也移入发布事务，消除校验-流转窗口。
> - 单 active 赛季从"先查后改"改为部分唯一索引兜底（迁移 0009 `uq_seasons_single_active`）+ `Activate` CAS，预检仅用于友好报错；唯一冲突经 `store.IsUniqueViolation` 映射 40901。

### T9 报名下单（校验链 + 事务）

**目标**：提交报名 = 校验链 → 事务内创建 registration + order。

**上下文**：无"待支付"状态；订单创建即拉起支付。**R1 已定稿**：提交时即插入 registration（status=`pending_payment`）+ order，支付成功回调中转 `active`（理由：身份唯一索引必须能拦住待支付窗口内的重复提交；若回调后才建 registration，同人双单都支付成功会撞唯一索引变成"付了钱报名失败"，体验更糟）。并发安全设计（已定稿，详细讨论见评审记录）：
- **身份维度**：`(player_id, group_id) WHERE status IN ('pending_payment','active')` 唯一索引，挡住同人同报名单元的并发/重复提交（跨微信同证件号命中同一 player，同样被拦）
- **名额维度**：用**一条原子条件 UPDATE 抢名额**，禁止"先 SELECT 查再 UPDATE 占"的两步写法（那是超卖根源）：
  ```sql
  UPDATE event_groups SET taken = taken + 1 WHERE id = ? AND taken < quota;
  -- RowsAffected = 1 → 抢到；= 0 → 满员，返回引导候补的错误码
  ```
- **请求幂等**：小程序每次点"提交报名"生成一次 `request_id`（UUID），重试复用同一 id；`UNIQUE(user_id, request_id)` 命中时直接返回已有订单，不重复创建
- 事务全程 `BEGIN IMMEDIATE`（读名额前即拿写锁），依赖 SQLite 单写入者串行化

- [x] `POST /registrations`：入参（event_id、level、dance_type、姓名、证件号、机构[可空]、request_id）
- [x] 校验链依次执行，每步明确错误码：赛事 registering → 身份证合法 → 年龄匹配组别 → 幂等键查重（有则直接返回已有订单）→ 该 group 已有本人进行中报名（撞唯一索引，拒：一人一组别）→ 原子 UPDATE 抢名额（taken < quota，失败返回特定码引导候补）
- [x] 事务内（BEGIN IMMEDIATE）：MatchOrCreatePlayer → 原子抢名额（UPDATE event_groups）→ 插入 registration(status=`pending_payment`) + order → 提交；任何一步失败回滚（含 taken 回退）
- [x] 错误码语义区分：幂等命中（返回原订单）/ 撞唯一索引（提示已有进行中报名）/ 名额已满（引导候补）——三者不可混为一个"报名失败"
- [x] 并发测试：①同人同时双请求，只有一个成功（另一个撞唯一索引/41004）；②同 request_id 重试只产生一个订单；③最后 1 个名额两并发请求只有一个抢到（RowsAffected 断言）；④取消后名额释放可立即重报 → **T9 无取消路径，留 T12 回归测试**（T12 已补：service `TestCancel_ReleasesSlotForConcurrentGrab`）
- [x] 单元测试：校验链每一环的失败分支、taken 计数器与 active 报名数的一致性对账
